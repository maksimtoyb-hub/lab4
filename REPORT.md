## 4. Ухвалені рішення

**Формат файлу.** `titanic.json` — NDJSON: файл розбивається на рядки, порожні рядки пропускаються, кожен рядок розбирається `JSON.parse`. Про всяк випадок програма також приймає JSON-масив (якщо вміст починається з `[`), тож вона не залежить від формату.

**Пошкоджений файл.** Якщо хоча б один рядок не є коректним JSON-об'єктом — відповідь 500 «Файл даних пошкоджений». Альтернатива — пропускати биті рядки, але тоді клієнт мовчки отримав би неповні дані.

**Конфлікт `-h`.** `program.helpOption('--help', ...)` — довідка доступна лише як `--help`, а `-h` віддано під `--host`.

**Перевірка порту.** `--port` має бути цілим числом 0–65535, інакше повідомлення й код завершення 1.

**Перевірка файлу при запуску** — `fs.access` з колбеком; якщо файлу немає: `Cannot find input file`, код 1.

**Параметри запиту.** Прапорець вмикається лише значенням рівно `true` (`?age=TRUE`, `?age=1` — вимкнено). У варіанті 6 немає числового параметра, тому код 400 не виникає; невідомі параметри ігноруються.

**Поле Survived** зберігається рядком (`"0"`/`"1"`), тому порівнюється після перетворення на число: `Number(r.Survived) === 1`.

**Відсутні, порожні й null-значення.**
- `Age` = `null` у 177 записах. При `?age=true` поле `age` виводиться зі значенням `null`, а не пропускається і не замінюється на 0: кожен об'єкт має однаковий набір ключів, а 0 був би неправдивим віком.
- Числові значення, записані рядками (`"22"`), перетворюються на числа; порожній або нечисловий рядок → `null`.
- Якщо в записі немає `Name` чи `Ticket`, поле дорівнює `null`; запис не відкидається.
- Запис без `Survived` при `?survived=true` не потрапляє у відповідь (немає підтвердження, що пасажир вижив).

**Коди помилок.**
| Ситуація | Код |
|---|---|
| Маршрут не `/` | 404 |
| Файл даних зник або не читається | 500 (це проблема сервера, а не запиту клієнта) |
| Файл пошкоджений | 500 |
| Не вдалося записати `--output` | 500 |

**--output.** Записується кожна відповідь (і успішна, і з помилкою), *до* відправлення клієнту, щоб помилку запису можна було повернути кодом 500.

**Стійкість сервера.** Усі помилки колбеків обробляються у стилі error-first; обробник додатково обгорнуто в try/catch для непередбачених синхронних помилок, тому сервер не падає.

### Помилкові запити
`curl -i "http://127.0.0.1:3000/abc"` → **404** `{"error": "Маршрут /abc не знайдено"}`

Файл перейменовано під час роботи сервера → **500** `{"error": "Файл даних не знайдено"}`

## Додаток. Короткі відповіді на питання до захисту

1. **HTTP** — текстовий протокол «запит–відповідь» прикладного рівня. Запит: метод + шлях + версія, заголовки, тіло. Відповідь: версія + код стану, заголовки, тіло. 200 — успіх, 400 — некоректний запит клієнта, 404 — ресурс не знайдено, 500 — внутрішня помилка сервера.
2. `http.createServer(handler)` створює сервер; в обробник передаються `req` (IncomingMessage) і `res` (ServerResponse). `listen(port, host, cb)` починає приймати з'єднання; `writeHead(code, headers)` надсилає рядок стану й заголовки; `end(body)` надсилає тіло й завершує відповідь.
3. `new URL(req.url, 'http://host')` → `url.pathname` і `url.searchParams.get(...)`. Рядок запиту — це текст, тому значення завжди рядки; число треба явно перетворити `Number(...)`.
4. `Content-Type` повідомляє тип і кодування тіла, щоб клієнт правильно його розібрав (JSON, UTF-8 для кирилиці).
5. JSON-документ — одне значення (тут масив) на весь файл; NDJSON — по одному JSON-об'єкту на рядок, весь файл не є коректним JSON; його можна читати й дописувати порядково.
6. Синхронний виклик блокує виконання до завершення; асинхронний лише запускає операцію, а результат приходить пізніше в колбек. `console.log` після `fs.readFile` виконається першим: колбек потрапляє в чергу й буде викликаний циклом подій лише коли стек викликів спорожніє.
7. `readFileSync` блокує потік і повертає дані; `readFile` не блокує і передає дані в колбек. Синхронний виклик в обробнику зупинив би обробку всіх інших запитів сервера.
8. Колбек — функція, передана аргументом іншій функції, щоб та її викликала. Передається як звичайне значення (`fs.readFile(p, cb)`). Колбек асинхронної функції виконується після завершення операції, коли стек викликів порожній.
9. Error-first: першим аргументом колбека є помилка (`null`, якщо все добре), далі результат. try/catch не перехоплює помилку з колбека, бо на момент її виникнення функція з try вже завершилась і її кадру немає в стеку.
10. `return` спрацьовує одразу, ще до того, як результат готовий. Результат передають далі через колбек — викликаючи наступну функцію всередині колбека.
11. Вкладаючи наступну дію в колбек попередньої (у main.js: readFile → обробка → writeFile → відповідь). «Пекло колбеків» — глибока драбина вкладень; зменшують іменованими функціями (`respond`, `handleRequest`), раннім `return` при помилці.
12. Стек викликів у повідомленні читається згори вниз: перший рядок — місце помилки з файлом:рядком. `node --inspect main.js ...` + `chrome://inspect`, або у VS Code «Run and Debug»: поставити точку зупину кліком ліворуч від рядка, переглядати змінні в панелі Variables.
13. Колбек викликається з циклу подій уже після завершення функції, що викликала `fs.readFile`, тож її кадру в стеку немає — стек «обірваний». Допомагають точки зупину всередині колбека й async stack traces у відлагоджувачі.
14. Необроблена помилка в обробнику (особливо в колбеку) завершує весь процес — сервер падає для всіх клієнтів. Запобігання: перевіряти `err` у кожному колбеку, try/catch для синхронного коду, завжди відповідати клієнтові кодом 500.
